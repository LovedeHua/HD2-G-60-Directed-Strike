# 官方版 vs 裁剪版：处理"标记虫洞"的逐点差异

> 对比基准：`etxp/HD2-G60-Smart-Targeting 0.1-beta.1`（上游，git 基线 commit `2879ef7`）
> vs 本工程 `g60-bughole-lock`。
> 日期：2026-09-27 ｜ 结论基于**实际读两边源码**，不是凭记忆。

---

## 一句话结论

**机制完全相同，本工程只在 4 个"决策点"上做了收窄 + 1 处判定放宽。**
换句话说：官方版能对虫洞做的事，本工程都能做，而且**比它多一处**（软信号判定）。

## 不同的部分

### ① 敌人侧：官方"主动挑敌人"，本工程"完全不管"（裁剪 A/C/D/E/F/G/H）

| | 官方版 | 本工程 |
|---|---|---|
| 敌人候选扫描 | `Candidates.capture` 每帧读 **5112 字节**候选记录 + 逐个 `entity()` | **删除**，不读 |
| 敌人优先级 | `Policy.choose` 从候选里按 rank 挑（泰坦/冲锋者/尖啸者…） | **删除** |
| `Filter.excluded` | 9 个资源（8 小虫 + Impaler 触手 + Hive Guard） | **整表清空** |
| `target_allowed` allowlist | `Allowlist(泰坦 + 弱点)`，非名单目标一律清 selection | **`nil`**（永不 veto） |
| `excluded` 判定 | `Filter.excluded(r) or not target_allowed(r)` | **恒 `false`** |
| priority/arrival/disposal 入口 | 对**所有** state-4 G-60 执行 | **只对本 mod 持有锁定的实体** |

**效果**：官方版会把 G-60 从引擎的原生 TargetLock 上抢过来打指定敌人；本工程完全不插手。

### ② 谁能走"爆点航点"（裁剪 C）

```lua
-- 官方：三类都算
has_weakpoint(r) = titan_profile(r) or weakpoint_profiles[r] or structure_profiles[r]
-- 本工程：只认第三类
has_weakpoint(r) = structure_profiles[r] ~= nil
```

`structure_profiles` 是**唯一**还带完整 `nodes/offset/belly_hash` 的一类，所以收窄安全。

### ③ 虫洞清单：13 条 → 17 条（裁剪 J）

- 上游 13 条 = 9 虫洞 + 3 tower（尖啸者巢/孢子菇×2）+ 1 egg（任务虫卵）
- 本工程 17 条 = 上游 9 虫洞 **+ 8 个可标记但上游漏收的变体**
  （`warrior_captive/_ceiling/_tutorial`、`scavenger_captive`、`bug_spawner_base`、
  尖啸者巢按上游原始参数恢复、`mechanical_bughole` ×2）
- 仍**不接管**：孢子菇 ×2、任务虫卵 ×1（不是虫洞）

### ④ ★★ 唯一一处"我们比官方更宽松"：target_valid 降级为软信号（裁剪 K）

这是**最重要的一处差异**，也是本工程与官方版的实质分歧。

官方版在**三处**把 `target_valid` 当硬否决：

| # | 位置 | 官方原文 | 后果 |
|---|---|---|---|
| 1 | `native_priority.lua:46` `eligible()` | `if not alive then forget_mark(); return false end` | 锁定被拒 |
| 2 | `native_priority.lua:68` structure mark | `if not alive then emit(NATIVE_TARGET_INVALID); forget_mark(); return end` | 不接管 |
| 3 | **`native_titan_aim.lua:70`** | `if not alive then target=nil;reason='Titan no longer alive' end` | **每飞行帧**置 nil ⇒ 永远算不出航点 |

`target_valid` 是 **game.dll+0x8858a0**，属于**游戏索敌系统**，回答
"引擎能不能把这实体当作**锁定目标**"。而虫巢**没有 `HealthComponent`**
—— 正是这一点让引擎原生索敌排除它们。

**本 mod 的核心恰恰是绕过索敌**（改导航目的地 + 直接调 `explode`），
官方却在三处仍用索敌的函数把关。本工程把这三处全部改为**软信号**：

```lua
-- target_valid 说 false 时做独立只读复核
local function readonly_alive(id, identity)      -- priority.lua
    local ok, again = pcall(d.entity, id)
    if not ok or not again then return false, 'ENTITY_GONE' end
    if again.identity ~= identity then return false, 'IDENTITY_CHANGED' end
    local okp = pcall(d.position, again)
    if not okp then return false, 'POSITION_UNREADABLE' end
    return true, 'ALIVE_BY_READ'
end
```

`titan` 阶段复用已有的 `Context.capture` 做复核（不引入新依赖）。
复核通过 ⇒ 继续接管并发 `structure_target_soft_invalid;context=NEW_MARK|ELIGIBLE|TITAN`。

**为什么这样更安全**：上游用 `target_valid` 是为了"不操作已死实体"（合理的工程保险）。
改成软信号后，**硬门槛变成纯只读校验**（实体可读 / `identity` 未变 / `unit` 未变 /
`pose.validate()` / 距离 < 200m —— 这些上游本来就有，只是被 `target_valid` 挡在前面）。
真正已死的实体仍然会被拒，只是不再误杀"引擎不认但实际存在"的虫巢。

### ⑤ 虫洞锁的忠实度（裁剪 I，官方没有的功能）

官方：`previous` 无论是敌人锁还是虫洞锁，**来新标记就抢占**
（注释写的是 "structure mark may interrupt an existing enemy lock"，但代码没区分）。

本工程：`previous.marked_structure` 时**先走 sticky 分支**，原巢确实不可用才改投。
理由：实机日志里 `#1083: 锁定562 -> 锁定559`（562 永久报废）—— 玩家连标多个巢时，
后标的会把前一个的 G-60 拉走。

## 行为对照表

| 场景 | 官方版 | 本工程 |
|---|---|---|
| 标记 1 个虫洞 | 接管 → 飞过去 → 引爆 | **相同** |
| 标记 1 个敌人（中小型） | 可能被 veto 打不了，或被自动优先级改打泰坦 | **完全交还引擎原生 TargetLock** |
| 标记 1 个泰坦/冲锋者 | 自动优先级会去打（无需标记） | **不插手**（除非它恰好被标记且在清单内） |
| 连标多个虫洞 | 后标的抢占前一个的 G-60 | **前一个的 G-60 保持忠实** |
| 标记孢子菇/任务虫卵 | 接管（structure_tower / structure_egg） | **不接管**（不是虫洞） |
| 标记尖啸者巢 | 接管（tower，参数 nodes=72） | **接管**（已按原始参数归入虫洞清单） |
| 标记 `mechanical_bughole` | 不接管（上游没这条） | **接管**（⚠ 参数是保守假设，未实机验证） |
| 目标原生 `target_valid=false` | **直接放弃** | **只读复核通过就继续** |
| 无任何标记 | 仍会每帧读候选、自动挑敌人 | **不读 Search、不写任何内存** |
